# AI Crawl Control

AI Crawl Control answers two questions for a site: which AI crawler families
fetch it, and what should happen to each one. The model mirrors Cloudflare's
AI Crawl Control, implemented on the sites PingWAF already knows:

- a **catalogue** of AI crawler families lives in the control plane
  (`api::ai_crawl::AI_BOTS`) — the data plane receives matching
  User-Agent patterns with the rule bundle, so no crawler list is compiled
  into the agent;
- a per-site **settings row** holds the feature switch, the default action
  and the two generated files (`robots.txt`, `llms.txt`);
- per-family **overrides** replace the default for a single crawler;
- a family hit produces a `security_events` row with
  `event_type = "ai_bot"` and one of the actions `allow` / `monitor` /
  `block`.

The feature is off by default (`enabled: false`, default action `monitor`);
a site with the feature disabled (or no settings row) compiles to zero
rules, so it costs nothing on the request path.

Storage: the `site_ai_crawl_settings` (one row per site) and
`site_ai_bot_policies` (one row per overridden family) tables, created by
migration 066.

## Endpoints

All endpoints require the admin JWT bearer token (the same `AdminUser`
authentication as the rest of the API); writes require the `write` role.

| Method & path | Purpose |
| --- | --- |
| `GET /api/v1/sites/{site_id}/ai-crawl` | The site's AI crawl settings plus the per-family override list |
| `PUT /api/v1/sites/{site_id}/ai-crawl` | Update settings and/or replace the override set |
| `GET /api/v1/sites/{site_id}/ai-crawl/preview?file=robots\|llms` | Render the generated file body without saving (`mode`, `content_type`, `body`) |
| `GET /api/v1/ai-crawl/catalog` | The crawler families PingWAF recognises (19) |
| `GET /api/v1/analytics/ai-crawlers` | Aggregated AI crawler traffic per family from `access_logs` |

### `GET /api/v1/sites/{site_id}/ai-crawl`

**Response (200):**

```json
{
  "enabled": true,
  "default_action": "monitor",
  "robots_mode": "generate",
  "robots_body": "# Generated by PingWAF\n...",
  "llms_mode": "off",
  "llms_body": "",
  "llms_include_routes": true,
  "cache_max_age": 3600,
  "content_signal_search": true,
  "content_signal_ai_train": false,
  "content_signal_ai_input": false,
  "policies": [
    { "bot_id": "gptbot", "action": "block" }
  ]
}
```

A site without a settings row reports the defaults: `enabled: false`,
`default_action: "monitor"`, both file modes `"off"`,
`llms_include_routes: true`, `cache_max_age: 3600`,
`content_signal_search: true`, `content_signal_ai_train: false`,
`content_signal_ai_input: false`, no policies.

### `PUT /api/v1/sites/{site_id}/ai-crawl`

Every field is optional; omitted fields keep their value.

| Field | Validation |
| --- | --- |
| `enabled` | boolean |
| `default_action` | `allow` / `monitor` / `block` |
| `robots_mode` / `llms_mode` | `off` / `generate` |
| `robots_body` / `llms_body` | at most 64 KiB (65 536 bytes); every CR (`\r`) is stripped on save |
| `llms_include_routes` | boolean — include the site's enabled routes as links in the generated llms.txt |
| `cache_max_age` | 0–86400 seconds (the `Cache-Control: max-age` of the served files) |
| `content_signal_search` / `content_signal_ai_train` / `content_signal_ai_input` | booleans — the Content Signals line advertised in the generated robots.txt |
| `policies` | when present, **replaces the whole override set**; each item needs a known `bot_id` from the catalogue and an `action` of `inherit` / `allow` / `monitor` / `block`; one row per family |

Validation failures answer `400 bad_request` with the offending field in
the message (`unknown AI crawler '…'`, `duplicate policy for '…'`,
`unknown default_action '…'`, `robots_body must be at most 65536 bytes`,
`cache_max_age must be between 0 and 86400`, …). A successful update also
touches the site and notifies the agents, so the new policy reaches the
data plane with the next rule bundle.

### The catalogue (`GET /api/v1/ai-crawl/catalog`)

19 families, each with `id`, `operator`, `name`, `category`
(`training` / `search` / `agent` / `other`) and the lowercase
`ua_substrings` that identify it. The catalogue is a control-plane
constant — adding a new crawler is a code change, not a migration.
The most recent addition is `facebookexternalhit` (Meta, category
`other`): the link-preview fetcher is its own family so it can be
observed or allowed independently of the Meta-ExternalAgent training
crawler. The list covers, among others: GPTBot, OAI-SearchBot,
ChatGPT-User (OpenAI); ClaudeBot, Claude-User, anthropic-ai (Anthropic);
PerplexityBot; Google-Extended; Applebot-Extended; CCBot (Common Crawl);
Bytespider (ByteDance); Amazonbot; Meta-ExternalAgent; facebookexternalhit;
cohere-ai; YouBot; Diffbot; ImagesiftBot; Timpibot.

## Actions and enforcement

`action` decides what happens when a request's User-Agent matches a
family's patterns (case-insensitive substring match):

| Action | Behaviour |
| --- | --- |
| `allow` | Request passes; nothing recorded beyond normal logging |
| `monitor` | Request passes; a `security_events` row with `event_type = "ai_bot"` is written |
| `block` | Request is denied with a `403` (through the challenge/decision pipeline) and a `security_events` row with `event_type = "ai_bot"` is written. Under deployment-wide **observation mode** the request is let through and only the event is recorded, like every other protection |

A per-family action of `inherit` defers to the site's `default_action`.
Matching happens against the raw `User-Agent` header; no pattern in the
catalogue is a prefix of another, so a family match is unambiguous. The
evaluation is independent of the traditional bot whitelist (bot
protection).

## Generated robots.txt / llms.txt

Both files have a mode: `off` (the origin's own file, if any, passes
through untouched) or `generate` (PingWAF serves its own file).

**`off` (or the whole feature disabled) means "the origin decides".** No
`mock` plugin is registered for `/robots.txt` or `/llms.txt`, so requests
to those paths are forwarded to the origin and answered entirely by it:
whatever the origin returns — a normal file, a redirect, or even a `403`
— is what the client sees. Such a `403` comes from the origin, not from
the WAF: it produces no `security_events` row and no WAF mitigation
header, so it should be triaged on the origin, not in the rule set.

**Where the file comes from.** The control plane renders the body at
configuration-build time — not per request — and pushes it to the data
plane with the rule bundle. The data plane serves it from an exact-path
`mock` plugin instance (`/robots.txt` and `/llms.txt`, status `200`,
`Content-Type: text/plain; charset=utf-8`,
`Cache-Control: public, max-age=<cache_max_age>`), registered ahead of the
WAF so a `robots.txt` request is answered before any inspection. An empty
body registers nothing — the origin's file passes through.

Consequences worth knowing:

- **Exact paths only.** `/robots.txt` and `/llms.txt` are matched
  literally; sub-paths are never intercepted, and no per-request string
  building happens on the request path.
- **CRLF filtering.** Saved bodies have every CR (`\r`) stripped, so a
  crafted body cannot smuggle header injection into the `mock` response.
- **64 KiB ceiling.** Bodies over `MAX_FILE_BYTES` (64 × 1024 bytes) are
  rejected with a `400`.

### Generated robots.txt

A `# Generated by PingWAF` / `# Site: <domain>` header, then one
`User-agent` block per overridden family (`Disallow: /` for `block`,
`Allow: /` otherwise), then the wildcard rule
(`User-agent: *` → `Disallow: /` when `default_action` is `block`,
`Allow: /` otherwise), and — when any Content Signals switch is on — a
`Content-Signal: search=<yes|no>, ai-train=<yes|no>, ai-input=<yes|no>`
line. The signal names follow the Content Signals convention
(`content_signal_search`, `content_signal_ai_train`,
`content_signal_ai_input`).

### Generated llms.txt

A `# <site name>` title, a summary line naming the site and domain, an
optional `## AI crawler policy` list (one `- <name> (<operator>,
<category>): <action>` line per override), and — when
`llms_include_routes` is on — a `## Pages` list linking the site's enabled
route paths.

## Analytics (`GET /api/v1/analytics/ai-crawlers`)

Aggregates AI crawler families over `access_logs` by matching the recorded
raw user agent against the catalogue's patterns, so the traffic panel shows
per-family request counts even for periods before the feature was enabled.
**Rows only exist for families with matching traffic inside the window** —
a family the catalogue knows but that sent no requests is absent, not
reported as zero. The window is given as explicit `from`/`to` (ISO 8601) or
as the shorthand `range=24h|7d|30d` (equivalent window; explicit
`from`/`to` wins when both are present; an unknown value answers
`400 invalid_range`). It is read-only reporting; enforcement lives in the
data plane.
