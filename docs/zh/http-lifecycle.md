# HTTP 请求生命周期

PingWAF 的数据面是基于 [Pingora](https://github.com/cloudflare/pingora) 的反向代理
（`pingap`）。每个请求都会沿固定的流水线阶段依次推进，而 PingWAF 的每一项功能都
挂接在其中一个确定的阶段上：

- **WAF 插件**（`pingwaf:waf`）在缓存之前、路由到上游之前运行，并在回程再次参与——
  因此命中缓存的响应也无法绕过检查；
- **质询插件**（`pingwaf:challenge`）在同一个早期阶段提供质询校验端点；
- **重写插件**（`pingwaf:rewrite`）与**缓存插件**（`pingwaf:cache`）在 location
  确定之后运行；
- **错误页插件**（`pingwaf:error_page`）只作用于响应；
- 站点级的 **HSTS** 与**强制 HTTPS** 插件分别作用于响应头与明文请求。

理解这个顺序，就能预测一条规则会做什么、以及调试一个请求为什么被放行、拦截或质询。
控制台的**请求生命周期**页面（`/lifecycle`）展示了同样的阶段。

## 流水线一览

```
客户端
  │  TLS 握手 —— SNI 选择证书、mTLS 客户端证书校验
  ▼
┌─ early_request ──────────────────────────────────────────────────────────┐
│  location 匹配（host + path）· 请求 ID · OpenTelemetry                    │
│  ▶ pingwaf:waf        站点策略、IP/地域、Basic Auth、Bot、限流、WAF 引擎  │
│  ▶ pingwaf:challenge  质询校验端点 /_pingwaf/challenge/verify             │
└──────────────────────────────────────────────────────────────────────────┘
  ▼
┌─ request ────────────────────────────────────────────────────────────────┐
│  ACME HTTP-01 / metrics 在本阶段应答（此前已通过 WAF）                    │
│  location 路径重写 · 未匹配 location → 404                                │
│  ▶ pingwaf:rewrite   请求头/路径/正文重写                                 │
│  ▶ pingwaf:cache     配置本次会话的缓存、处理 PURGE                       │
└──────────────────────────────────────────────────────────────────────────┘
  ▼
┌─ 缓存查找（pingora 内置） ────────────────────────────────────────────────┐
│  HIT → 直接返回缓存响应（WAF 已在上面检查过）                              │
│  MISS → 继续                                                            │
└──────────────────────────────────────────────────────────────────────────┘
  ▼
┌─ 上游 ───────────────────────────────────────────────────────────────────┐
│  proxy_upstream 插件 · 负载均衡选后端 · 连接（可重试）                     │
│  upstream_request_filter 追加 X-Forwarded-* · 请求体大小限制（413）      │
└──────────────────────────────────────────────────────────────────────────┘
  ▼
┌─ 上游响应 ───────────────────────────────────────────────────────────────┐
│  上游响应头到达 · 缓存写入决策                                            │
│  ▶ pingwaf:error_page  用站点自定义错误页替换上游错误响应                  │
└──────────────────────────────────────────────────────────────────────────┘
  ▼
┌─ 响应 ───────────────────────────────────────────────────────────────────┐
│  ▶ pingwaf:error_page  · pingwaf:waf 记录状态供访问日志                   │
│  ▶ 每站点的 HSTS 响应头插件 · 缓存头（Age 等）                             │
└──────────────────────────────────────────────────────────────────────────┘
  ▼
┌─ 响应体 ─────────────────────────────────────────────────────────────────┐
│  ▶ pingwaf:waf  流结束时发出访问日志（含响应体采样）                      │
│  响应体重写插件（升级为 WebSocket 的 101 之后跳过）                        │
└──────────────────────────────────────────────────────────────────────────┘
  ▼
┌─ fail_to_proxy（仅出错时） ───────────────────────────────────────────────┐
│  错误分类：502 上游错误 / 499 客户端断开 / 408 读取超时 / 400 非法头       │
│  内置错误模板渲染（不运行插件，自定义错误页不生效）                        │
└──────────────────────────────────────────────────────────────────────────┘
  ▼
┌─ logging ────────────────────────────────────────────────────────────────┐
│  pingap 访问日志（PingWAF 的日志在更早的阶段已经发出）                     │
└──────────────────────────────────────────────────────────────────────────┘
```

## 阶段详解

| # | 阶段 | Pingora 钩子 | 该阶段发生什么 |
| --- | --- | --- | --- |
| 0 | TLS / 连接 | *（HTTP 之前）* | SNI 选择证书；当任一站点启用 mTLS 时，监听层按受信 CA 的并集校验客户端证书。站点级强制在 WAF 插件内完成。 |
| 1 | 早期请求 | `early_request_filter` | 匹配 location（host + path），创建请求 ID 与追踪上下文，随后**运行全部 `early_request` 插件**：WAF 插件的完整检查链和质询校验端点。此处应答的插件会短路后续所有阶段。 |
| 2 | 请求 | `request_filter` | ACME HTTP-01 质询、metrics 端点与管理 API 在此应答——它们在 `early_request` 插件**之后**，所以这些请求只要匹配到 location，也一样先过 WAF。然后是 location 级路径重写与 **`request` 步骤插件**：重写插件、缓存插件（为本次会话配置 pingora 的 HTTP 缓存并处理 `PURGE`）。未匹配任何 location 的请求直接 `404`，不运行任何插件。 |
| 3 | 缓存查找 | `proxy_cache` | Pingora 内置的 HTTP 缓存。**命中即结束请求**、不触及上游——但前提是 WAF 已检查过。未命中则继续。 |
| 4 | 上游 | `proxy_upstream_filter`、`upstream_peer`、`connected_to_upstream`、`upstream_request_filter`、`request_body_filter` | 运行 `proxy_upstream` 步骤插件；负载均衡选择后端（连接失败可重试）；追加 `X-Forwarded-*` 类请求头；请求体流式转发、超限返回 `413`。 |
| 5 | 上游响应 | `upstream_response_filter`、`upstream_response_body_filter` | 上游响应头到达：pingora 判定响应能否写入缓存，设置 `X-Request-Id`，错误页插件可将上游错误响应（400 及以上，含 502/504）替换为站点配置的页面。 |
| 6 | 响应 | `response_filter`、`response_body_filter` | 运行 `response` 步骤插件：错误页插件获得第二次机会；WAF 插件记录状态与大小供访问日志使用；站点 HSTS 插件添加 `Strict-Transport-Security`；缓存头（`Age` 等）在此写入。响应体过滤器可改写正文——但 `101 Switching Protocols` 升级之后跳过的字节是 WebSocket 流量而非 HTTP 正文。流结束时 WAF 插件发出访问日志条目（按站点日志设置采样响应体）。 |
| 7 | 失败 | `fail_to_proxy` | 仅在出错时触发：分类为 `502`（上游错误）、`499`（客户端断开）、`408`（读取超时）或 `400`（非法请求头），并用 pingap 内置错误模板渲染。此处**不运行任何插件**，自定义错误页同样无法替换该页面。 |
| 8 | 日志 | `logging` | pingap 最后写入自己的访问日志。PingWAF 的日志条目在做出决定的那一刻就已经发出（见[调试](#调试与生命周期)）。 |

插件的**步骤**（step）名与配置键 `step` 一一对应（`early_request`、`request`、
`proxy_upstream`、`upstream_response`、`response`）。PingWAF 注入插件时使用固定
步骤：WAF 与质询插件在 `early_request`，重写与缓存在 `request`，错误页插件在响应路径上。

## WAF 插件内部

PingWAF 的大部分策略都在 WAF 插件内执行。检查按以下顺序进行，**任何一个环节做出
应答，请求即告结束**：

| # | 检查 | 配置位置 | 行为 |
| --- | --- | --- | --- |
| 1 | 站点暂停 | 站点列表 | 暂停的站点立即返回暂停页，后续检查不再运行。 |
| 2 | mTLS 客户端证书 | 站点 → SSL/TLS | 缺失或无效的客户端证书 → 拦截（站点级强制；TLS 监听层只校验 CA 并集）。 |
| 3 | IP 与地域规则 | 站点 → 安全 → 访问控制 | 首条匹配生效。动作：`block`、`allow`、`challenge`、`js_challenge`，或 `basic_auth`（推迟到第 4 步）。 |
| 4 | Basic Auth | 站点 → 安全 → 访问控制 | 站点级开启，或由 IP/地域规则触发。密码错误时有小幅延迟；未认证返回 `401` 页面。`hide_credentials` 会在转发前移除 `Authorization` 头。 |
| 5 | Bot 防护 | 站点 → 安全 → Bot 防护 | 按 User-Agent 分类：放行、拒绝（拦截页）或仅记录。 |
| 6 | 速率限制 | 站点 → 安全 → 速率限制 | 固定窗口计数，规则可基于 IP、Host、路径、请求头、Cookie 等特征。超限时执行规则动作；`challenge` 动作按配置下发 clearance cookie。 |
| 7 | WAF 引擎 | 站点 → 安全 → WAF | 规则检测（签名 + 表达式 + 异常分值）。结论：放行、监控（仅记录）、拦截、质询。 |

两条贯穿性行为值得记住：

- **观察模式**（站点 → 安全 → WAF）会把第 3、5、6、7 步的拦截/质询全部降级为
  “本应拦截”的记录事件。**不**降级的内容：站点暂停、mTLS 与 Basic Auth——它们是
  强制执行的配置，而不是检测结果。
- 第 1–6 步的拒绝直接用生成的页面应答，不会经过错误页插件（见[阶段 6](#阶段详解)），
  因此自定义错误页不会替换 WAF 的拦截/质询页。

## 质询子系统

`pingwaf:challenge` 与 WAF 插件共用一个待质询存储：

- 拦截/质询结论返回 JS 质询页（`503`）或硬拦截（`403`）；
- 质询页把工作量证明提交到 `/_pingwaf/challenge/verify`，该端点由质询插件在
  `early_request` 阶段提供；
- 校验通过后访客获得签名的 clearance cookie，之后的请求在过期前跳过质询；
- 难度、放行时长与质询级别是站点级设置（站点 → 安全 → CC 防护）。

## 缓存与 WAF

阶段 1–3 的顺序是刻意设计的：**WAF 会检查每一个请求，包括将要由缓存响应的请求**。
缓存配置来自站点的缓存规则（站点 → 缓存）；命中与否在第 3 阶段决定，此时 WAF 与
重写插件已经运行过，因此缓存命中无法绕过安全检查，WAF 的拦截也始终优先于缓存响应。

## 响应修改与缓存

当一个响应既要被缓存、又要被修改时，**修改发生在哪个阶段**决定缓存里存的是什么：

- **上游阶段（缓存写入之前）** —— `upstream_response_filter` /
  `upstream_response_body_filter` 的修改会进入缓存副本。原始 pingap 中，
  compression 插件（压缩后的正文会被缓存）以及配置了
  `mode = "upstream"` 的 `response_headers` 都属于这一类。
- **响应阶段（缓存写入之后）** —— `response_filter` /
  `response_body_filter` 的修改在**每次服务时**重新应用，包括缓存命中：
  缓存响应同样会运行 response 过滤器（只跳过 upstream 过滤器），因此客户端
  总能拿到修改后的响应，而缓存副本保持上游的原始字节。PingWAF 的重写响应
  规则与站点 HSTS 响应头都走这条路，永远不会写进缓存。
- **错误页替换不会被存储** —— 插件在替换响应时发送
  `Cache-Control: private, no-store`：页面照常返回，但不会写入缓存。

实际含义：在响应阶段修改响应（PingWAF 重写规则）不会改变缓存内容——修改会在
每次请求（包括缓存命中）时重新执行；若希望修改后的内容进入缓存，需要在上游
阶段完成修改。

## 调试与生命周期

从**日志**页开始，再沿流水线排查：

- **请求没有 WAF 记录** —— 该请求没有匹配任何 location（阶段 2 的 `404`，不运行
  任何插件）。缓存命中**不是**原因：WAF 已在阶段 1 检查过请求、访问日志照常发出
  （只是响应体来自缓存而非回源）。
- **证书签发失败** —— ACME HTTP-01 请求在阶段 2 应答，但在此之前先经过
  `early_request` 插件：拦截 `/.well-known/acme-challenge/*` 的 IP 或限流规则也会
  拦截证书续期。
- **请求被拦截或质询** —— 安全事件里记录了命中的规则和触发的检查（上表第 3–7 步）。
  生成式响应（拦截、质询、暂停页）的访问记录在请求阶段即刻发出，状态码为真实值。
- **“本应拦截却没有”** —— 检查观察模式、规则优先级、IP/地域规则的首条匹配语义，
  以及是否有更早的 `allow` 规则先行命中。
- **“自定义错误页没有生效”** —— 设置 → 错误页中的页面只替换**上游**错误响应
  （阶段 5）。WAF 的拦截/质询页在上游被联系之前就已生成；`fail_to_proxy`
  （阶段 7）的代理失败页面在渲染时不运行任何插件——两者都不会被自定义页
  替换，保持内置样式。
- **“上游从没收到请求”** —— 在日志里找最后经过的阶段：缓存命中（阶段 3）、WAF
  应答（阶段 1），或请求体大小限制的 `413`（阶段 4）。
